# Folder Structure — where every file goes

Every project follows the same rules, so the **folder and the file name tell you what a class is**
before you open it.

## The rules

1. **One class per file, file named after the class.** `AvatarUploadViewModel` → `AvatarUploadViewModel.cs`.
2. **The namespace matches the folder.** `Models/ValidationAttributes/` → `FileUploadPortal.Models.ValidationAttributes`.
3. **Technical roles end in their role:** `...ViewModel`, `...Attribute`, `...Controller`, `...Service`,
   `...ModelBinder`, `...ViewComponent`, `...HealthCheck`, `...BackgroundService`, `...Extensions`,
   `...Settings`, `...DbContext`, `...Store`, `...Event`, `...Exception`, `I...Repository`.
4. **Business things keep their business name** (`Product`, `Book`, `Money`, `BankAccount`); their
   **folder** says what kind they are (`Data/Entities/`, `ValueObjects/`, `Aggregates/`).
   `ProductEntity` or `MoneyValueObject` would only add noise — and in DDD the code should use the
   same words the business uses.

## MVC / web projects

| Folder | Holds only | Example |
|---|---|---|
| `Controllers/` | Controllers | `ProductsController.cs` |
| `Models/` | **View models only**: what a view displays or a form posts. Always `...ViewModel`. | `ProductFormViewModel.cs`, `CartPageViewModel.cs` |
| `Models/ValidationAttributes/` | Validation attributes used on view models | `MaximumFileSizeValidationAttribute.cs` |
| `Data/` | Where data is kept: `DbContext`s and in-memory stores | `LibraryDbContext.cs`, `ProductStore.cs` |
| `Data/Entities/` | What gets **stored** (database rows or in-memory records) | `Product.cs`, `Book.cs` |
| `Data/Interceptors/` | EF Core interceptors | `SqlQueryLoggingInterceptor.cs` |
| `Data/Migrations/` | Generated by `dotnet ef` — don't edit by hand | |
| `Services/` | Classes that *do* work for controllers | `CategoryService.cs`, `Services/Email/SmtpEmailSender.cs` |
| `Settings/` | Classes bound from `appsettings.json` | `ShopSettings.cs` |
| `Constants/` | `const` values | `FeatureNames.cs` |
| `Filters/` | MVC action filters | `RequireFeatureFlagAttribute.cs` |
| `ModelBinders/` | Custom model binders | `CustomIsoDateFormatModelBinder.cs` |
| `ViewComponents/` | View component classes (their HTML is in `Views/Shared/Components/`) | `RecentActivitySidebarViewComponent.cs` |
| `HealthChecks/` | `IHealthCheck` implementations | `CatalogDatabaseHealthCheck.cs` |
| `BackgroundServices/` | `BackgroundService` classes | `EmailSendingBackgroundService.cs` |
| `Extensions/` | Extension-method classes | `SessionJsonExtensions.cs` |
| `SessionState/` | Classes stored in the user's session | `ShoppingCart.cs` |
| `Views/` | Razor `.cshtml` files (see [RAZOR_BASICS.md](RAZOR_BASICS.md)) | |
| `wwwroot/` | Static files served as-is (CSS, uploads) | |

### Why view models are separate from entities

A form should only be able to change the fields we put on it. If a form binds straight to the
stored class, a user can add extra fields to the request (e.g. `Role=Admin`, `Id=7`) and model binding
will happily set them — this is called **over-posting**. A `...ViewModel` only has the allowed fields,
plus things the page needs that are never stored (dropdown choices, error messages).

The controller copies values between the two. Pages that only **display** data (a product list) may
use the entity directly — there's nothing to post.

## DDD domain (Project 4.2)

| Folder | Holds |
|---|---|
| `ValueObjects/` | Compared by value, never change: `Money` |
| `Aggregates/` | Entities that guard business rules: `BankAccount` |
| `Events/` | Facts that happened (`...Event`) and `IDomainEventDispatcher` |
| `Exceptions/` | Business-rule errors (`...Exception`) |
| `Repositories/` | Storage *interfaces* (`I...Repository`) — implemented outside the domain |
| `Services/` | Orchestrates load → act → save → send events: `BankAccountService` |

## Tests

| Folder | Holds |
|---|---|
| `Fakes/` | Hand-written stand-ins for interfaces (`FakeAccountRepository`) |
| `Fixtures/` | Shared setup used by many tests (`ProductCatalogWebsite`: server + browser) |
| *(project root)* | The test classes themselves (`...Tests.cs`) |

## Small console apps (2.1, 5.1, 5.2, 4.2's demo)

These are deliberately **one `Program.cs` file**. Their few classes are at the bottom of that file
(a note at the top lists them). Splitting a 200-line demo into folders would make it harder to read.
